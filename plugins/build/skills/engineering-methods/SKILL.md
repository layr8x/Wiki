# 개발 방법론

디자이너와 기획자가 개발팀과 합의할 때 쓰는 기준이다. 코드를 쓰기 위한 것이 아니라
**무엇을 요구하고 무엇을 확인할지** 알기 위한 것이다.

## 고르는 법

| 상황 | 쓸 것 |
|---|---|
| 팀 속도를 재고 싶음 | DORA 4지표 |
| 무엇을 얼마나 테스트할지 | 테스트 피라미드 |
| 문제가 났는데 원인을 모름 | 관측가능성 3기둥 |
| 위험한 변경을 내보내야 함 | 점진적 배포(= 실제 사이트에 올리는 일) |
| 장애가 반복됨 | 비난 없는 사후 분석 |
| 코드를 계속 못 고치겠음 | 기술 부채 정리 |

## 방법론

**DORA 4지표**(구글 DevOps Research and Assessment)
배포 빈도, 변경 소요 시간, 변경 실패율, 복구 시간. 네 개로 팀 속도와 안정성을 잰다.

속도와 안정성이 상충한다는 통념을 수년간의 조사로 뒤집은 연구다. **잘하는 팀은 둘 다 좋다.**
느리게 가는 팀이 안전한 게 아니라, 자주 조금씩 내보내는 팀이 실패도 적고 복구도 빠르다.
기획 쪽에서 이 지표가 쓸모 있는 지점은 일정 협의다. "왜 이렇게 오래 걸리나요"를
"변경 소요 시간의 어느 구간이 긴가요"로 바꿔 물으면 답이 구체적으로 온다.
네 지표를 한꺼번에 요구하지 말고 복구 시간부터 물어보는 게 대화가 잘 풀린다.

**테스트 피라미드**(마이크 콘)
작고 빠른 검사를 많이, 느리고 전체를 도는 검사를 조금.
화면 전체를 도는 검사만 잔뜩 있으면 느리고 자주 깨져서 아무도 안 본다.

**관측가능성 3기둥**
기록(무슨 일이 있었나), 지표(얼마나 자주 얼마나 오래), 추적(요청 하나가 어디를 거쳤나).
겉지표가 초록인데 실제로 안 되는 상황은 이 셋 중 빠진 게 있어서 생긴다.

**점진적 배포**
카나리는 일부 사용자에게만 먼저 내보내고, 블루그린은 새 판을 옆에 세웠다 한 번에 바꾼다.
되돌리는 데 걸리는 시간이 짧을수록 더 자주 안전하게 내보낼 수 있다.

**멱등성**(= idempotent, 같은 작업을 여러 번 해도 결과가 같은 성질)
같은 작업을 여러 번 해도 결과가 같은 성질.
재시도가 안전해지므로 실패해도 그냥 다시 부르면 된다. 수집이나 저장에서 특히 중요하다.

**비난 없는 사후 분석**(blameless postmortem)
장애 뒤에 사람이 아니라 조건을 본다. "누가 실수했나"가 아니라 "왜 그 실수가 가능했나".
사람을 탓하면 다음 장애는 보고되지 않는다.

**12 요소 앱**(Twelve-Factor App)
"내 컴퓨터에선 되는데요"를 구조로 막는 관행 모음. 설정을 코드 밖에 둔다는 항목이 특히 자주 쓰인다.

**기술 부채**(워드 커닝햄)
빨리 가려고 미룬 정리에는 이자가 붙는다. 부채 자체가 아니라 **갚을 계획 없이 지는 게** 문제다.

## 요구할 때 쓰는 문장

- "되돌리는 데 얼마나 걸리나요"
- "이게 실패하면 사용자에게 어떻게 보이나요"
- "같은 요청이 두 번 들어가면 어떻게 되나요"
- "이 변경으로 깨질 수 있는 화면은 어디인가요"

## 하지 말 것

- 개발 용어를 그대로 옮겨 적고 이해했다고 하기
- 검사 없이 완료로 보고받기
- 급하다고 점진적 배포를 건너뛰기. 급할수록 되돌릴 길이 필요하다
