# 바이브 코딩 실전 가이드 ① 시작하기

> **바이브 코딩 실전 가이드 시리즈** (개발을 몰라도, AI에게 지시해 만들고 운영하기)
> ① 시작하기 (이 문서) · ② GitHub · ③ Supabase · ④ Vercel

> 📌 **한 줄 요약**
> "바이브 코딩"은 코드를 직접 타이핑하는 대신 **AI에게 말로 지시해서** 프로그램을 만드는 방식입니다.
> 그렇게 만든 결과물은 여전히 **코드 창고(GitHub)** · **데이터 보관함(Supabase)** · **사이트 자동 게시(Vercel)** 세 곳에 얹혀 돌아갑니다.
> 이 문서는 그 큰 그림이고, 각 서비스 사용법은 이어지는 상세 가이드 3개에 있습니다.

이 문서는 **개발을 전혀 몰라도** 읽을 수 있게 쓰였습니다. 어려운 말이 나오면 바로 옆 괄호에 쉬운 풀이를 붙였습니다.

---

## 1. 바이브 코딩이 대체 뭔가요?

**바이브 코딩(vibe coding)** = 사람이 코드를 한 줄 한 줄 타이핑하지 않고, AI에게 **"이런 걸 이렇게 만들어줘"라고 평소 말로 지시**하면 AI가 대신 코드를 짜주는 개발 방식입니다. (2025년 이후 크게 퍼진 방식으로, 비개발자도 만들 수 있게 된 것이 핵심입니다.)

비유하면 이렇습니다.

| | 예전 방식 (전통 코딩) | 바이브 코딩 |
|---|---|---|
| 집 짓기에 비유하면 | 벽돌을 직접 하나하나 쌓음 | **"큰 창문 있는 거실 하나 만들어줘"** 라고 말하면 AI 목수가 알아서 지음 |
| 사람이 하는 일 | "어떻게(코드 문법)" 까지 전부 | **"무엇을 · 왜"** 에 집중 (판단·검수·방향) |
| 기획자에게 | 진입 장벽 높음 | 말로 지시하니 참여 가능 |

즉 바이브 코딩에서 **기획자의 역할이 오히려 커집니다.** "무엇을 만들지, 왜 만들지, 잘 만들어졌는지"를 판단하는 사람이 중심이 되기 때문입니다.

---

## 2. 그런데 왜 이 세 서비스를 알아야 하나요?

"AI가 다 해준다면서 왜 GitHub·Supabase·Vercel을 배워야 하죠?" 라는 의문이 자연스럽습니다. 답은 이렇습니다.

AI가 코드를 **만들어주긴** 하지만, 그 결과물은 어딘가에 **보관하고 · 저장하고 · 실제로 공개**해야 진짜 서비스가 됩니다. 그 세 가지를 담당하는 곳이 바로 이 셋입니다.

집을 짓고 운영한다고 생각하면 쉽습니다.

| 서비스 | 비유 | 하는 일 |
|---|---|---|
| **GitHub** (깃허브) | 설계도 보관소 + 공사 일지 | AI가 만든 코드(= 설계도)를 보관하고, 누가 언제 무엇을 바꿨는지 전부 기록 |
| **Vercel** (베르셀) | 자동 시공사 | 설계도가 바뀌면 자동으로 건물(웹사이트)을 새로 지어 "입주"시킴 (= 인터넷에 공개) |
| **Supabase** (슈파베이스) | 창고 + 관리사무소 | 건물 안에서 쓰는 데이터(짐)를 보관하고, 출입증(로그인)을 발급·관리 |

**이 셋을 이해하면 AI에게 더 정확히 지시할 수 있습니다.** (예: "이 데이터는 Supabase의 어느 표에 저장해줘", "이 변경은 미리보기로 먼저 배포해줘" 처럼요.) 그래서 바이브 코딩을 잘하려면 이 세 곳의 "지도"를 알아두는 게 큰 무기가 됩니다.

---

## 3. 세 개가 어떻게 맞물려 돌아가나 (핵심 흐름)

AI(또는 개발자)가 코드를 한 번 고치면, 아래 순서로 자동으로 이어집니다.

```
① AI에게 "이렇게 고쳐줘" 지시 → 코드 수정
        │
        ▼
② GitHub 에 올림 (백업 + 변경 기록)
        │
        ▼
③ Vercel 이 그걸 감지해서 웹사이트를 자동으로 다시 지음 (배포)
        │
        ▼
④ 완성된 사이트가 인터넷에 공개됨 (sdij-wiki.vercel.app)
        │
        ▼
⑤ 사이트는 필요할 때마다 Supabase 에서 데이터·로그인 정보를 가져다 씀
```

한 줄 요약: **코드가 GitHub에 올라가면 → Vercel이 자동으로 사이트를 새로 띄우고 → 그 사이트는 Supabase 창고에서 데이터를 꺼내 쓴다.**

## 4. 우리 회사는 이 위에서 뭘 운영하나

현재 이 3종 세트 위에서 **서비스 3개**가 돌아갑니다.

| 우리 서비스 | 쉽게 말하면 | 주로 쓰는 곳 |
|---|---|---|
| **AMS 위키** (sdij-wiki) | 직원용 사내 매뉴얼·가이드 검색 사이트 | Vercel(사이트) + Supabase(가이드 데이터·로그인) |
| **카카오 챗봇** | 학부모 카카오톡 문의를 자동 분류해 저장 | Supabase(데이터·자동작업) |
| **카카오 상담 수집** | 학원-학부모 카카오 상담을 실시간 수집·분석 | Supabase(데이터·자동작업) |

세 서비스의 **코드는 전부 GitHub 한 곳**(`layr8x/Wiki` 저장소)에 모여 있습니다.

---

## 5. 기획자는 각 서비스에서 주로 뭘 하게 되나

코드를 짜는 게 아니라, **"확인하고 · 요청하고 · 상태를 보는"** 용도가 대부분입니다.

| 서비스 | 기획자가 실제로 하는 일 (예시) |
|---|---|
| **GitHub** | 할 일·버그를 글로 등록(이슈), 변경 검토 요청(PR) 읽고 의견 남기기, 변경 이력 확인 |
| **Supabase** | 저장된 데이터를 표처럼 조회, 상담 수집량 확인, 로그인 사용자 확인 |
| **Vercel** | 배포가 잘 됐는지(초록불) 확인, 변경 사항 "미리보기" 링크로 먼저 보기, 방문 통계 |

각각을 어떻게 하는지는 이어지는 문서 3개에 단계별로 정리했습니다.

## 6. 공통 안전 수칙 (세 서비스 전부 해당)

개발을 모르는 상태에서 **아래만 지키면 사고는 안 납니다.**

1. **"삭제 / Delete / 빨간 버튼"은 누르지 않기.** 확인 차 눌러보는 것도 금지입니다. 지우면 되돌리기 어려운 게 많습니다.
2. **비밀값(키·토큰·비밀번호)은 화면에 있어도 복사해서 밖으로 보내지 않기.** 카카오톡·메일·외부 문서에 붙여넣는 순간 유출입니다.
3. **설정(Settings) 화면은 눈으로만.** 값을 바꾸기 전에 개발자(또는 AI)에게 먼저 물어보세요.
4. **헷갈리면 멈추고 물어보기.** "이거 눌러도 돼요?"가 사고보다 백배 낫습니다.
