# 바이브 코딩 실전 가이드 ② GitHub

> **바이브 코딩 실전 가이드 시리즈**: ① 시작하기 · **② GitHub (이 문서)** · ③ Supabase · ④ Vercel

> 📌 **한 줄 요약**
> GitHub(깃허브)는 **코드의 "구글 드라이브 + 변경 이력 장부"** 입니다.
> AI나 개발자가 만든 코드를 전부 보관하고, "누가·언제·무엇을·왜" 바꿨는지 기록합니다.
> 기획자는 여기서 주로 **할 일 등록(이슈)** 과 **변경 검토(PR) 읽기**를 하게 됩니다.

---

## 1. GitHub가 뭔가요? (비유)

문서를 여러 명이 같이 고치면 `기획서_최종.doc`, `기획서_최종_진짜최종.doc`, `기획서_최종_이게진짜.doc` 처럼 파일이 엉키죠. GitHub는 그 문제를 코드에서 완전히 해결한 도구입니다.

- **코드를 한 곳에 안전하게 보관** (구글 드라이브처럼)
- **모든 변경을 사진 찍듯 기록** (되돌리기 가능, "누가 왜 바꿨는지"까지)
- **여러 명이 동시에 작업해도 안 엉킴** (각자 사본에서 고치고 합침)

우리 회사 코드는 전부 **`layr8x/Wiki`** 라는 하나의 "저장소"에 들어 있습니다. (위키·카카오 챗봇·카카오 수집 3개 서비스 코드가 다 여기 있습니다.)

## 2. 접속 준비 (처음 한 번만)

### 1단계. 계정 만들기
**https://github.com/signup 에서 회원가입** 합니다. (회사 메일 권장)

### 2단계. 초대받기 (제일 중요)
우리 저장소는 **비공개(private)** 라, 가입만 해서는 안 보입니다.
- **관리자(사장님)에게 "제 GitHub 아이디는 OOO 입니다. Wiki 저장소에 초대해 주세요" 라고 요청**하세요.
- 초대가 오면 메일 또는 https://github.com/notifications 에서 **"Accept invitation"(초대 수락)** 을 누릅니다.

> 관리자 입장 참고: `layr8x/Wiki` → Settings → Collaborators → Add people 에서 아이디로 초대. 권한은 보통 **Read(읽기)** 또는 **Triage(이슈 관리)** 면 기획자에게 충분합니다.

### 3단계. 2단계 인증 켜기 (보안 필수)
비밀번호가 새도 계정을 지키는 잠금장치입니다.
- **Settings → Password and authentication → Two-factor authentication → Enable** 을 눌러 휴대폰 인증앱으로 설정하세요.

### 접속 확인
로그인 후 **https://github.com/layr8x/Wiki** 가 열리면 성공입니다. 코드 목록이 보입니다.

## 3. 화면 둘러보기 (상단 탭 지도)

저장소에 들어가면 위쪽에 탭들이 있습니다. 기획자가 알아야 할 것만 추립니다.

| 탭 | 우리말 | 여기서 뭘 하나 |
|---|---|---|
| **Code** | 코드 | 실제 파일·폴더 보기 (문서도 여기 있음). 읽기 위주 |
| **Issues** | 이슈 | **할 일 · 버그 · 요청을 글로 등록**하는 곳 (기획자 주 무대) |
| **Pull requests** | 풀 리퀘스트(PR) | **"이렇게 바꿨는데 봐주세요" 검토 요청.** 읽고 의견 남기기 |
| **Commits** | 커밋(변경 기록) | 언제 무엇이 바뀌었는지 시간순 기록 (Code 화면 안에 있음) |
| **Settings** | 설정 | ⚠️ 기획자는 들어가지 않습니다 |

> 📷 (컨플루언스에 실제 화면 캡처를 넣으면 더 좋습니다: 저장소 첫 화면 + 상단 탭)

## 4. 기획자 실전: 이런 걸 하게 됩니다

### 실전 A. 할 일 · 버그를 등록하기 (이슈)
가장 많이 쓰는 기능입니다. "이거 고쳐주세요", "이런 기능 추가해주세요"를 글로 남깁니다.

1. **Issues 탭 → 초록색 `New issue` 버튼** 클릭
2. **제목**에 한 줄 요약 (예: "챗봇 결제내역 날짜가 안 보여요")
3. **본문**에 상황을 구체적으로: 어디서 / 무엇을 했더니 / 어떻게 됐는지 + (가능하면) 화면 캡처를 끌어다 붙이기
4. **`Submit new issue`** 클릭

> 💡 캡처는 본문 칸에 이미지를 **드래그해서 놓으면** 자동으로 올라갑니다.

### 실전 B. 변경 검토 요청(PR) 읽고 의견 남기기
개발자나 AI가 뭔가 바꾸면 "PR"이 올라옵니다. 기획자는 그게 의도대로인지 확인하고 의견을 답니다.

1. **Pull requests 탭**에서 해당 항목 클릭
2. 맨 위 설명을 읽어 **"무엇을 왜 바꿨는지"** 파악
3. **`Files changed` 탭**에서 실제 바뀐 내용 확인 (빨강=지운 줄, 초록=추가한 줄)
4. 의견은 **`Conversation` 탭 맨 아래 코멘트 칸**에 남기고 `Comment` 클릭

### 실전 C. "언제 뭐가 바뀌었지?" 이력 확인
1. **Code 탭 → 시계 모양 `History` 또는 커밋 개수(예 "163 commits")** 클릭
2. 시간 역순으로 변경 기록이 뜹니다. 하나를 클릭하면 그때 정확히 뭐가 바뀌었는지 보입니다.

### 실전 D. 문서·내용 읽기
Code 탭에서 폴더를 눌러 들어가 `.md`(문서) 파일을 클릭하면 읽기 좋게 표시됩니다. (이 가이드도 `docs/바이브코딩-가이드/` 안에 있습니다.)

## 5. 절대 하지 말 것 (안전선)

| 하지 말 것 | 이유 |
|---|---|
| **`main` 브랜치의 파일을 직접 편집(연필 아이콘)해서 저장** | main은 실제 서비스에 바로 반영되는 "정본"입니다. 잘못 저장하면 사이트가 깨질 수 있어요 |
| **`Settings` 안의 값 변경** | 저장소 권한·연동·삭제 등 위험한 설정이 모여 있습니다 |
| **빨간 글씨 버튼 (Delete repository 등)** | 저장소 자체가 사라질 수 있습니다 |
| **아무 파일이나 지우기(Delete)** | 코드 한 줄이 서비스 전체를 멈추게 할 수 있습니다 |

기획자는 **"이슈 쓰기 · PR 읽고 코멘트 · 이력/문서 읽기"** 까지만 하면 사고가 날 일이 없습니다.

## 6. 용어 사전 (자주 나오는 말)

| 용어 | 쉬운 뜻 |
|---|---|
| 저장소 (Repository, 레포) | 한 프로젝트의 코드가 통째로 든 폴더. 우리는 `layr8x/Wiki` |
| 커밋 (Commit) | 변경 사항을 "사진 한 장 찍어 저장"한 단위. 메시지로 이유를 남김 |
| 브랜치 (Branch) | 원본을 안 건드리고 작업하는 "사본 작업 공간". `main`이 정본 |
| PR (Pull Request) | "내 사본에서 이렇게 바꿨으니 정본에 합쳐 주세요" 검토 요청 |
| 머지 (Merge) | 검토가 끝난 PR을 정본(main)에 실제로 합치는 것 |
| 이슈 (Issue) | 할 일·버그·요청을 적어두는 글. 댓글로 논의 가능 |
| 리뷰 (Review) | PR을 보고 승인/수정요청/의견을 남기는 것 |

## 7. (참고) 개발자·AI는 실제로 어떻게 연결하나

기획자는 웹 화면만으로 충분하지만, "AI가 코드를 올린다"는 게 뒤에서 어떻게 되는지 궁금하실 수 있어 짧게 적습니다. (안 읽으셔도 됩니다.)

1. 개발자(또는 바이브 코딩 AI)는 GitHub 저장소를 자기 컴퓨터로 **복제(clone, = 통째로 내려받기)** 합니다.
2. 코드를 고친 뒤 **커밋(저장)** 하고 GitHub로 **푸시(push, = 올리기)** 합니다.
3. 이때 비밀번호 대신 **토큰(token, = 일회용 출입 열쇠 문자열)** 으로 인증합니다. (이 토큰이 바로 밖으로 새면 안 되는 비밀값입니다.)
4. 올린 변경은 보통 **PR**로 만들어 검토를 거친 뒤 `main`에 머지합니다.

즉 기획자가 화면에서 보는 "이슈·PR·이력"은, 개발자·AI가 위 과정으로 만들어 둔 결과물입니다.

## 8. 문제가 생기면

| 증상 | 이렇게 하세요 |
|---|---|
| 로그인은 됐는데 우리 저장소가 안 보임 | **초대 수락**을 안 했을 가능성. 관리자에게 재초대 요청 |
| "404" 페이지가 뜸 | 주소가 틀렸거나 권한이 없음. 관리자에게 확인 |
| 뭔가 잘못 눌렀나 걱정됨 | **아무것도 더 누르지 말고** 화면을 캡처해 개발자에게 문의 |

> 확신이 안 서면 언제든 **"이거 눌러도 돼요?"** 라고 먼저 물어보세요. 그게 항상 정답입니다.
