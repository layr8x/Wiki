## 0. 한눈에 보기

- 흩어져 쌓이기만 하던 카카오 상담 채팅을 **분석 가능한 데이터로 수집·정리**하고, 그 데이터로 **챗봇 도입 효과(1차 50~60%·2차 80~88% 대체)와 FAQ 개선안, 화면 개선 문의**까지 이어냈습니다.
- 단순 수집·집계가 아니라, **수집 데이터에 숨어 있던 품질 문제(개인정보·자동분류 중단·집계 기준 모호·키워드 오염)를 직접 찾아 해결**했습니다.
- AI를 "답을 대신 써 주는 도구"가 아니라 **"대규모 판단을 나눠 맡기고 서로 교차검증하게 하는 분석 파트너"**로 활용했습니다. 전체 상담 1,658건을 사람이 다 읽는 대신, 다중 에이전트로 전수 분류하고 적대적 검증·통계·라이브 재조회로 신뢰도를 확보했습니다.
- 초기 추정치가 실제와 다르다는 것을 **스스로 발견해 전수 사실로 교정**했고, "분석을 위한 분석"이라는 피드백을 받고 **행동·시연 중심으로 방향을 바꾼** 경험이 있습니다.

## 1. 배경과 문제 인식

학원 상담은 전화(실장 기록), 카카오 파트너 채팅 등 여러 창구로 흩어져 있었습니다. 특히 카카오 채팅은 **쌓이기만 할 뿐 분석 가능한 형태로 정리돼 있지 않았고**, "챗봇이 상담을 얼마나 대체할 수 있는가"라는 질문에 답할 근거가 없었습니다.

핵심 질문은 다음과 같았습니다.

- 학부모·학생이 카카오로 가장 많이 묻는 것은 무엇인가?
- 그중 챗봇이 지금 풀 수 있는 것과 못 푸는 것은 어디까지인가?
- 그래서 챗봇을 오픈해야 하는가, 무엇을 먼저 만들어야 하는가?

이 질문에 답하려면 먼저 **대화를 모아 성격별로 나눌 수 있어야** 했습니다. 여기서 프로젝트가 시작됐습니다.

## 2. 목표

1. 카카오 파트너 채팅을 **실시간으로 수집해 분석용 데이터베이스에 적재**한다.
2. 적재한 데이터를 **상담 성격별로 전수 분류**해 챗봇 도입 효과와 개선 방향의 근거로 만든다.
3. 근거를 **의사결정 자료(오픈 여부)와 실행 산출물(FAQ·화면 개선)**로 연결한다.

## 4. 단계별 상세 - 과정 · 발견한 문제 · 해결 · 결과

### 4-1. 수집·적재

**과정**
- 카카오 파트너(비즈니스 채팅) 상담을 수집해 Supabase 데이터베이스에 적재했습니다.
- 저장 구조를 두 층으로 설계했습니다. **대화 단위(`kakao_partner_chats`)**와 **메시지 단위(`kakao_partner_messages`)**로 나누고, **원본(raw)도 함께 보관**해 나중에 재가공할 수 있게 했습니다.
- 채널(마이클래스·LIVE 등)은 프로필 값으로 구분되게 했고, 보낸이(고객·상담원·시스템), 시각, 메시지 유형을 함께 저장했습니다. 자동분류(category)·감성(sentiment) 컬럼도 두었습니다.

**발견한 문제 → 해결**
- 문제: 원본 채팅에 **전화번호·이름 같은 개인정보(PII)**가 그대로 들어 있어, 그대로 분석·공유하면 안 됐습니다.
  - 해결: 원문은 분류 처리에만 쓰고 **산출물에는 집계·분류 결과만** 남기는 원칙을 세웠습니다. 분석이 끝난 원문 작업 파일은 즉시 폐기했습니다. (작업 중 안전장치가 원문 저장을 막은 적도 있어, 명시적으로 "분류 후 폐기·집계만 저장" 절차를 확정했습니다.)

**결과**: 재원생 카카오 대화가 대화·메시지 단위로 조회 가능한 형태로 적재됐습니다(마이클래스 채널 누적 약 1,600여 대화).

### 4-2. 원본 확보·복호화 (전화 상담 연계)

**과정**
- 비교 기준으로 쓸 전화 상담(AMS 실장 기록)은 **암호로 잠긴 엑셀** 원본이었습니다.
- Python으로 **복호화(msoffcrypto) → 적재(openpyxl) → 집계**를 자동화했습니다.

**발견한 문제 → 해결**
- 한글 파일명이 자모 분리(NFC/NFD) 방식 차이로 검색에 안 잡히는 문제 → **유니코드 정규화**로 해결.
- 집계 수치 신뢰성 → **openpyxl과 pandas로 각각 독립 집계해 대조하는 2중 검증**을 적용(불일치 0).
- 중복 상담 ID → **번호 기준 중복 제거**.

**결과**: 6월 전화 상담 81,863건을 전수 집계(의도별 조회 20.1%·처리 31.6%·컨설팅 37.5%·혼합 10.8%).

### 4-3. 데이터 정합 점검 (문제 발견이 가장 많았던 단계)

수집 데이터를 그냥 쓰면 안 되는 함정을 직접 찾아냈습니다.

- **함정 1 - 자동분류가 멈춰 있었다.**
  - category(상담 유형 자동분류) 컬럼의 분류 시각을 확인해 보니 **2026년 6월 17일 한 시점 이후로 갱신이 멈춰** 있었습니다. 그 결과 6월 대화의 **38%가 미분류** 상태로 방치돼 있었습니다.
  - 해결: 이 컬럼에 의존하지 않고 **원문 기반으로 다시 분류**했고, 분류 배치가 멈춘 것 자체를 **운영 이슈로 별도 보고**했습니다.
- **함정 2 - 대화 수 기준이 두 가지였다.**
  - "6월 대화 수"가 세는 방법에 따라 달랐습니다. 6월에 **시작된** 대화(132건)와 6월에 **메시지가 오간(활동)** 대화(162건)가 달랐습니다.
  - 해결: **"6월에 활동한 대화(162건)"**로 기준을 통일하고, 기존 분석과 정확히 일치함을 확인했습니다.
- **함정 3 - 분류 축이 섞여 있었다.**
  - 표면 주제별 분류(입반·계정·출결 등 12종)와 "챗봇이 해결 가능한가" 기준 분류(조회·처리·계정·사람·노이즈 5종)는 **다른 축**인데 혼동하기 쉬웠습니다.
  - 해결: 두 축을 명확히 분리해 문서에 표기하고, 겹쳐 보이는 숫자에 주의를 달았습니다.
- **함정 4 - 키워드 집계가 오염돼 있었다.**
  - "학원 연락처 문의"를 키워드로 세었더니 24.1%로 나왔는데, 정밀 재확인하니 계정 문의의 '제 전화번호가…' 언급이 섞인 값이었고 **실제는 2.8%**였습니다.
  - 해결: 키워드를 정밀화해 재집계하고, 오염 사례를 문서에 남겨 과대 집계를 막았습니다.

### 4-4. 전수 분류

**과정**
- 6월 대화 162건을 시작으로, **전체 기간 1,658건까지 대화를 한 건씩 성격별로 분류**했습니다.
- 사람이 1,658건을 다 읽는 것은 비효율적이라, **여러 AI 에이전트에게 구간을 나눠(28개 배치) 동시에 분류**시켰습니다.

**발견한 문제 → 해결**
- 문제: AI가 "조회로 해결 가능"이라고 **과대 분류**할 위험(대체율 부풀림).
  - 해결: 분류 뒤 **별도의 적대적 검증 에이전트**가 "정말 조회로 끝나는가"를 엄격히 재확인해 애매한 건을 강등했습니다. **6월은 14건, 전체는 191건**이 강등됐습니다.
- 문제: 초기에 카테고리 단위로 **추정**한 수치(조회 34%·계정 22%)가 실제와 달랐습니다.
  - 해결: 추정을 버리고 **대화 전건 정독(census)**으로 다시 산출(조회 12%·계정 39%). "추정이 틀렸다"는 것을 스스로 발견해 교정하고, 모든 문서를 census 기준으로 일원화했습니다.

**결과**: 카카오 역량별 분류 확정 - 6월(조회 12%·처리 29%·계정 39%·사람 11%·노이즈 10%), 전체(조회 8%·처리 28%·계정 52%·사람 10%·노이즈 2%).

### 4-5. 검증 (3중)

수치를 상급자 의사결정 자료로 쓰려면 틀리면 안 됐습니다.

- **독립 재집계**: 원본에서 모든 핵심 수치를 다시 계산해 대조(불일치 0건).
- **통계적 불확실성 표기**: 표본이 162건으로 작다는 점을 인정하고 **Wilson 95% 신뢰구간**으로 "약 50%(43~58%)"처럼 범위를 함께 표기.
- **라이브 재조회**: 운영 데이터베이스를 직접 다시 조회(6월 163건)해 재분류했고, 기존 수치와 오차범위 안에서 일치함을 확인.

### 4-6. 활용

수집·분류·검증한 데이터를 실제 결과물로 연결했습니다.

- **챗봇 도입 효과 보고서**: 1차(조회+계정 수정) 50~60%, 2차(+처리) 80~88% 대체. 오픈 여부 판단 근거. (컨플루언스 "도입 효과_26.06")
- **데이터 기반 FAQ 추가안**: 가장 많이 묻는 계정·로그인 등 18개 항목과 답변, 7탭 구성.
- **로그인 전/후 답변 구성**: 계정 문의(44.5%)가 로그인 전에 생기므로 앱 밖(로그인 화면)에 답을 두는 설계.
- **화면 개선 문의**: FAQ·로그인·AMS 챗봇 디자인을 데이터와 대조해 검증하고 보완 문의 작성.
- **피드백 반영**: "분석을 위한 분석"이라는 지적을 받고, **행동·효과 1장 + 실제 화면 시연**으로 전환.

## 6. AI 활용 방법 총정리

AI를 쓴 방식은 **"대규모 판단을 나눠 맡기고, 서로 교차검증하게 하는 분석 파트너"**였습니다.

| 활용 | 구체적으로 한 것 |
|---|---|
| 자동화 | 암호화 원본 복호화·재집계를 코드로 자동화 |
| 대규모 분류 병렬화 | 1,658개 대화를 28개 구간으로 나눠 여러 에이전트가 동시 분류 |
| 적대적 검증 | 분류 결과를 다른 에이전트가 반박·재검증해 과대분류 차단 |
| 독립 검증 | 별도 에이전트가 원본에서 수치를 재계산해 교차 확인 |
| 라이브 조회 | 운영 DB(Supabase)를 직접 SQL로 조회해 드리프트 확인 |
| 통계 적용 | 소표본 불확실성을 Wilson 신뢰구간으로 정량화 |
| 화면 대조 | 실제 챗봇 화면을 렌더해 데이터·디자인과 1:1 검증(시연 필름스트립) |
| 방법론 차용 | CRISP-DM·민감도·시나리오·RICE·피라미드 원칙 등 |

핵심은 **AI의 결과를 그대로 믿지 않고, AI로 AI를 검증하게 한 것**입니다(분류 → 적대검증 → 재집계 → 라이브 재조회, 4중). 이 구조 덕분에 사람이 다 읽을 수 없는 양을 다루면서도 신뢰할 수 있는 수치를 만들었습니다.

## 8. 배우고 느낀 점

- **수집은 절반이고, 데이터를 믿을 수 있게 만드는 것이 나머지 절반이었습니다.** 자동분류 중단·집계 기준 차이·개인정보·키워드 오염처럼 겉으로 안 보이는 문제를 먼저 찾는 것이 분석의 질을 좌우했습니다.
- **AI를 잘 쓰는 것은 "얼마나 많이 시키느냐"가 아니라 "어떻게 검증하게 하느냐"**였습니다. 분류-적대검증-재집계-라이브재조회로 겹겹이 확인하는 구조가 가장 효과적이었습니다.
- **정직한 수치가 결국 가장 강했습니다.** 초기 추정이 틀렸다는 것을 스스로 드러내 교정했고, 소표본은 신뢰구간으로 범위를 밝혔습니다. 이 태도가 상급자 의사결정 자료로서 신뢰를 만들었습니다.
- **"분석을 위한 분석"을 경계하게 됐습니다.** 방법론을 쌓기보다, 결정과 행동으로 연결하고 실제 화면으로 증명하는 것이 중요하다는 피드백을 실제로 반영했습니다.
