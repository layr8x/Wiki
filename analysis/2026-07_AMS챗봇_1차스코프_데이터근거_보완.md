# AMS 챗봇 LLM 툴 우선순위 설계 데이터 근거 보고서

## 의사결정 요약 (가장 먼저 읽을 것)

7월 8일 회의의 핵심 안건은 "LLM에 어떤 툴을 붙이고, 그 툴들을 어떤 우선순위로 쓰게 할 것인가"였습니다. 이 질문에 대한 답은 다음과 같습니다.

1차(7월 16일)는 LLM에 붙는 툴이 위키 가이드 검색 하나뿐입니다. 툴이 하나라 우선순위를 정할 필요가 없고, 대신 이 하나뿐인 툴이 실제 문의에서 얼마나 자주 실패할지가 관건입니다. 확인 결과, 상담량 3위 카테고리인 LIVE(14.8%)에서는 검색할 콘텐츠 자체가 없어 이 툴이 거의 항상 실패합니다. 1차 오픈 전에 LIVE 관련 콘텐츠부터 채워야 합니다.

2차에서 붙일 툴의 우선순위는 상담 데이터로 답할 수 있습니다. 학생 출결 조회 툴을 최우선으로 붙여야 합니다(해당 카테고리 상담의 56.8%가 단순 조회로 끝남). 그다음이 결제·납부 조회 툴입니다. 반대로 입반 상담·대기자 관리·퇴원 상담은 툴을 붙여도 사람의 판단이 필요한 비중이 커서(각각 85.4%, 86.2%, 52.7%가 조회 아닌 처리·컨설팅) 우선순위를 낮게 잡아야 합니다.

툴 사이의 라우팅(언제 위키 검색 툴을 쓰고, 언제 학생 데이터 툴로 넘어가고, 언제 사람에게 넘길지 판단하는 로직)은 이미 설계 개념이 코드에 있습니다. `src/components/chatbot/intents.js`에 "신뢰도 70% 미만이면 명확화 질문 또는 에스컬레이션"이라는 임계값이 정의되어 있지만, 실제로 이 값을 보고 분기하는 코드는 아직 연결되어 있지 않습니다. 2차 설계 시 이 개념을 재사용하되, 실제로 배선하는 작업이 필요합니다.

## 배경 및 목적

7월 8일 회의에서 개발자는 AMS 챗봇의 LLM에 어떤 툴을 붙이고 어떤 우선순위로 답변을 만들지를 논의했습니다. 1차(7월 16일)는 위키 가이드 검색 툴 하나만 붙이고 세션을 유지하지 않는 가장 단순한 형태로, 2차(일정 미정)에서 학생 데이터 조회 툴과 상담 자동 요약 툴을 추가하기로 했습니다. 회의록은 방향성과 리스크를 정확히 짚었으나, 툴 우선순위를 정하는 데 필요한 아래 질문들은 실제 데이터로 검증되지 않은 상태로 남아 있었습니다.

1. 2차에서 어떤 툴부터 붙여야 하는지(어떤 상담 카테고리가 툴로 자동 완결되기 쉬운지)
2. 1차의 유일한 툴(위키 검색)이 어느 카테고리에서 실패할 가능성이 높은지
3. 툴 간 라우팅(우선순위 판단) 로직을 새로 설계해야 하는지, 재사용 가능한 기존 개념이 있는지
4. 토큰/비용 통제를 정말 새로 설계해야 하는지, 아니면 재사용 가능한 기존 코드가 있는지

이 보고서는 위 질문 각각에 대해 저장소에 이미 존재하는 전화상담 분석 데이터와 Supabase 데이터베이스, 챗봇 코드를 직접 조회하여 답합니다. 코드 변경은 없으며, 모든 조회는 읽기 전용(SELECT)으로 수행했습니다.

중요한 전제: 마이클래스 챗봇, AMS 위키 AI 의미검색 등 이 저장소에 구현된 관련 서비스는 모두 프로토타입 단계이며, 실제 운영 트래픽에 노출된 적이 없습니다(작성자 확인). 따라서 이 서비스들에서 조회되는 사용량·조회수·비용 관련 수치는 실사용 지표가 아니라 시연·개발 단계에서 만들어진 값일 수 있습니다. 이 보고서는 이 전제를 반영해 각 데이터가 실사용 실측인지, 프로토타입 단계의 참고값인지를 장별로 명확히 구분합니다.

## 요약 (결론 먼저)

**1. 2차에서 붙일 툴의 우선순위는 상담 카테고리별 조회·처리·컨설팅 비중으로 정할 수 있습니다.** 출결 관리(29.7%, 조회 56.8%)가 툴로 자동 완결되기 가장 쉬운 카테고리라 최우선 후보이고, 결제·납부가 다음입니다. 입반 상담·대기자 관리·퇴원 상담은 물량은 크지만(각각 22.8%, 7.1%, 8.7%) 사람의 판단이 필요한 비중이 커서 툴을 붙여도 효과가 제한적입니다.

**2. 1차의 유일한 툴(위키 검색)은 LIVE 카테고리에서 실패할 가능성이 매우 높습니다.** 상담량 3위(14.8%, 6개월 누적 65,617건)인 LIVE에 대응하는 위키 콘텐츠가 정식 가이드·FAQ를 합쳐도 사실상 없습니다. 툴 우선순위 이전에, 이 유일한 툴이 작동할 콘텐츠부터 채워야 합니다.

**3. 툴 간 라우팅(우선순위 판단) 로직의 설계 개념은 이미 코드에 있지만 배선되어 있지 않습니다.** `intents.js`에 "신뢰도 70% 미만이면 명확화 질문 또는 에스컬레이션"이라는 임계값이 정의되어 있으나, 실제로 이 값을 읽어 분기하는 코드는 없습니다. 2차에서 여러 툴(위키 검색, 학생 데이터 조회) 사이의 우선순위를 정할 때 이 개념을 재사용할 수 있습니다.

**4. 토큰/비용 통제 코드는 이미 있지만, 실제 트래픽으로 검증된 값은 아닙니다.** 재원생용 AI 검색 기능(api/search-summary.js)에 IP당 분당 20회 요청 제한, 응답 최대 토큰 500~700 제한 등이 이미 구현되어 있습니다. 다만 이 기능 역시 프로토타입이라 제한 값이 적절한지 실측된 적은 없습니다.

**5. 위키 실사용 데이터는 사실상 전무합니다.** 가이드 135건의 조회수·도움됨 수는 실제 사용 흔적이 아니라 초기 구축 시 넣어둔 시연용 값입니다. 검색 로그 테이블(search_logs, guide_views, guide_feedback)은 셋 다 0행이라, 툴 우선순위가 실제로 맞았는지 검증할 데이터가 아직 없습니다.

## 3. 1차 유일 툴(위키 검색)의 콘텐츠 공백

### 3-1. 두 가지 콘텐츠 소스와 그 관계

이번 조사 과정에서 위키의 검색 대상 콘텐츠가 한 곳이 아니라 두 곳으로 나뉘어 있다는 점을 확인했습니다.

- Supabase `guides` 테이블: 135건. 조회수·도움됨 수 컬럼이 있는 정식 콘텐츠(SOP, 정책, 트러블슈팅 등)입니다. 다만 이 컬럼의 실제 값은 5-1장에서 다루듯 시연용 고정값이라 실사용 여부의 근거로는 쓸 수 없습니다.
- 정적 검색 인덱스(`api/_lib/guide-index.js`): 181건. 현재 운영 중인 AI 의미검색 기능이 실제로 참조하는 카탈로그로, 위 135건에 더해 FAQ 형식 46건이 추가로 포함되어 있습니다.

이 46건의 FAQ는 `guides` 테이블에 없기 때문에 조회수 추적이 되지 않지만, 내용을 직접 확인한 결과 "출석을 결석으로 변경하고 싶어요", "대기 명단은 어디서 확인하나요" 같은 실무형 질문·답변으로 구성되어 있어 실질적인 가치는 충분합니다. 즉 위키 콘텐츠의 진짜 규모는 135건이 아니라 181건이며, 이 중 26%(46건)는 조회수 데이터가 전혀 없는 사각지대라는 점을 감안해야 합니다.

## 4. 툴 라우팅(우선순위 판단) 로직, 설계 개념은 있으나 미배선

2차에서 위키 검색 툴에 더해 학생 데이터 조회 툴, 상담 자동 요약 툴을 추가하면, LLM은 하나의 질문에 어떤 툴을 먼저 시도할지 판단해야 합니다. 예를 들어 "결석 처리하고 싶어요"라는 질문이 오면, 위키 검색 툴로 일반 절차를 안내할지, 학생 데이터 조회 툴로 그 학생의 실제 출결 상태를 확인할지, 아니면 확신이 낮아 사람에게 넘길지 정해야 합니다. 이 판단 로직(라우팅)을 처음부터 새로 설계해야 하는지 확인했습니다.

저장소 코드(`src/components/chatbot/intents.js`)를 직접 확인한 결과, 관련 설계 개념이 이미 존재합니다. 이 파일은 `CONFIDENCE_THRESHOLD = 0.70`이라는 상수를 정의하고 "70% 미만이면 명확화 질문 또는 에스컬레이션(Watson 표준)"이라는 주석을 달아두었습니다. 다만 이 값을 읽어서 실제로 분기하는 코드는 이 파일 안에 없습니다. 즉 "신뢰도가 낮으면 사람에게 넘긴다"는 설계 의도는 있지만, 그 의도를 실행하는 배선은 아직 없습니다.

같은 파일의 의도 분류 로직도 참고할 수 있습니다. 미리 정의된 25개 문답(공식 Q&A)을 먼저 점수로 매칭하고, 거기서 안 잡히면 키워드 규칙을 순서대로 하나씩 검사해 처음 맞는 것을 채택하는 구조입니다(신뢰도는 규칙마다 미리 정해둔 고정값이며, 질문마다 새로 계산되지 않습니다). 이 구조 자체는 여러 툴 사이의 우선순위 문제가 아니라 여러 키워드 규칙 사이의 우선순위 문제를 다루고 있어, 2차의 툴 라우팅에 그대로 쓸 수는 없습니다. 하지만 "신뢰도 임계값으로 자동응답과 에스컬레이션을 가른다"는 개념 자체는 재사용할 수 있습니다.

정리하면, 2차 툴 라우팅 설계에서 새로 만들 것과 재사용할 것이 나뉩니다. 재사용 가능: 신뢰도 임계값(70%)으로 자동응답 여부를 가르는 개념. 새로 만들어야 함: 그 임계값을 실제로 판단에 연결하는 코드, 그리고 툴이 여러 개일 때(위키 검색 vs 학생 데이터 조회) 어느 것을 먼저 시도할지 정하는 라우팅 로직 자체(현재는 툴이 하나뿐이라 이 문제가 아직 발생하지 않았습니다).

근거: `src/components/chatbot/intents.js` 직접 확인(CONFIDENCE_THRESHOLD 상수, 25문답 우선 매칭 후 키워드 규칙 순차 검사 구조).

## 5. 위키 실사용 현황과 검색 로그 공백

### 5-1. guides 테이블의 조회수는 실사용 지표가 아닙니다

Supabase guides 테이블을 조회하면 가이드별로 조회수·도움됨 수가 들어 있어(135건 중 20건이 조회수 1 이상, 누적 조회수 5,487회), 얼핏 실사용 데이터처럼 보입니다. 하지만 저장소 코드(supabase/seed.sql, supabase/generate-seed.mjs)를 직접 확인한 결과, 이 숫자들은 초기 구축 단계에서 사람이 직접 입력한 고정값입니다. 예를 들어 "환불 승인 기준 판단 가이드"의 조회수 567, 도움됨 45는 seed.sql의 INSERT 문에 그대로 박혀 있는 값으로, 실제 직원이 567번 열람했다는 근거가 전혀 아닙니다.

작성자 확인대로 이 프로젝트 관련 서비스가 모두 프로토타입 단계라는 점과도 일치합니다. 즉 "어떤 가이드가 실제로 많이 조회되는지"는 이 데이터로 알 수 없으며, 1차 챗봇의 QA 우선순위를 "조회수 상위 20건" 기준으로 정하는 것은 근거가 없는 접근입니다. 대신 3장에서 확인한 콘텐츠 존재 여부(커버리지 공백)와 아래 5-2의 검색 로그 부재 자체를 우선순위 판단의 근거로 삼아야 합니다.

### 5-2. 검색 로그 자체가 존재하지 않습니다

`search_logs`, `guide_views`, `guide_feedback` 세 테이블을 직접 조회한 결과 모두 0행입니다. 스키마는 2026년 5월 26일 마이그레이션으로 이미 만들어져 있지만, 실제로 로그가 쌓이고 있지 않습니다. 즉 "직원이 위키에서 무엇을 검색했는지", "AI 의미검색에 어떤 질문을 던졌는지"를 보여주는 데이터가 이 시점까지 전혀 없습니다.

이 보고서의 2장(상담 카테고리별 비중)은 이 공백을 메우기 위해 전화상담 데이터를 대리 지표로 사용한 것입니다. 다만 실제 위키 검색 패턴은 전화상담 패턴과 다를 가능성이 있습니다. 예를 들어 상담실장은 자주 처리하는 절차는 이미 숙지하고 있어 위키를 찾지 않고, 오히려 드물게 발생하는 예외 상황에서만 위키를 검색할 수도 있습니다. 1차 챗봇 배포 시점부터 검색 질의와 결과를 실제로 로그에 남기도록(이미 만들어진 search_logs 테이블에 insert 로직 연결) 개발 범위에 포함할 것을 권고합니다. 이렇게 하면 2차 고도화 우선순위를 추측이 아닌 실측 데이터로 정할 수 있습니다.

## 6. 토큰 비용, 접근 제어의 기존 코드와 그 한계

회의에서 "향후 새로 설계가 필요하다"고 언급한 항목들에 대응하는 코드가 이미 이 저장소의 다른 기능(api/search-summary.js, 재원생 앱의 AI 검색)에 구현되어 있습니다.

| 회의에서 언급한 리스크 | 기존 코드의 대응 방식 |
|---|---|
| 분당 토큰 사용량 제어, 악의적·과도한 쿼리 방지 | IP당 분당 20회 요청 제한(인메모리 버킷) |
| 비용 폭증 방지 | 응답 최대 토큰 500~700으로 제한, 저비용 모델(Claude Haiku 4.5) 사용, 프롬프트 캐싱으로 반복 비용 절감 |
| 요청 크기 제한 | 요청 본문 8KB 상한 |

다만 이 코드 역시 프로토타입 단계라는 점을 반영해 두 가지로 나누어 볼 필요가 있습니다. 첫째, "이런 종류의 제어가 필요하다"는 설계 자체는 이미 검토·구현되어 있으므로 2차에서 처음부터 다시 설계할 필요는 없습니다. 둘째, 그러나 "분당 20회", "최대 토큰 500~700" 같은 구체적인 수치는 실제 트래픽이나 비용 데이터로 검증된 값이 아니라 프로토타입 단계에서 정한 가정값입니다. 1차가 실제로 열려 사용량이 발생하면 이 수치들을 실측 기반으로 다시 조정해야 합니다.

2차 고도화에서 새로 설계가 필요한 부분은 이 코드 패턴을 "직원별·등급별 권한 제어"까지 확장하는 것입니다. 기존 코드는 IP 기준 제한이라 사용자(직원) 식별 기준이 아닙니다. 회의에서 언급한 "AMS 메뉴 권한과 챗봇 데이터 접근 권한의 1:1 매핑"을 구현하려면 IP 기준에서 로그인 사용자 기준 제한으로 바꾸는 작업이 필요하며, 신규 설계가 필요한 범위는 이 부분과 위에서 언급한 수치 재조정으로 한정됩니다.

## 7. 종합 결론

이번 조사로 회의에서 논의한 "LLM에 어떤 툴을 붙이고 어떤 우선순위로 쓸지"에 데이터로 답할 수 있게 됐습니다. 1차는 툴이 위키 검색 하나뿐이라 우선순위 문제가 아직 발생하지 않으며, 2차에서 붙일 툴의 우선순위는 학생 출결 조회 툴, 결제·납부 조회 툴 순입니다. 다만 그대로 진행할 경우 네 가지 구체적인 위험이 있습니다.

첫째, 1차 유일 툴의 실패 지점입니다. 상담량 3위 카테고리인 LIVE에 대응하는 위키 콘텐츠가 정식 가이드와 FAQ를 합쳐도 사실상 없습니다. 이 상태로 1차를 오픈하면 챗봇의 체감 완성도가 실제 개발 품질과 무관하게 낮게 평가될 수 있습니다.

둘째, 라우팅 로직 미배선입니다. "신뢰도가 낮으면 사람에게 넘긴다"는 설계 개념(신뢰도 70% 임계값)은 코드에 있지만 실제로 연결되어 있지 않습니다. 2차에서 툴이 여러 개로 늘어나면 이 배선 없이는 어느 툴을 먼저 시도할지, 언제 사람에게 넘길지 판단할 수 없습니다.

셋째, 측정 공백입니다. 위키 검색 로그가 전혀 쌓이고 있지 않아 툴 우선순위 설계가 실제로 맞았는지 검증할 데이터가 없습니다. 1차 개발과 함께 로그 적재를 시작해야, 2차 설계 시점에는 추측이 아닌 데이터로 판단할 수 있습니다.

넷째, 데이터 오인 위험입니다. guides 테이블의 조회수·도움됨 수는 시연 단계에서 넣어둔 고정값일 뿐 실사용 지표가 아닌데, 겉보기에는 실측 데이터처럼 보입니다. 이 값을 실사용으로 오인해 QA 우선순위나 콘텐츠 투자 결정을 내리면 잘못된 판단으로 이어질 수 있으므로, 1차 오픈 전에 이 값을 초기화하거나 명확히 구분 표시해야 합니다.

이 네 가지를 1차 개발 범위와 2차 설계에 반영하면, 7월 16일 목표 자체를 바꾸지 않고도 툴 우선순위 설계의 리스크를 크게 줄일 수 있습니다.

- 툴 라우팅 설계(4장)는 intents.js의 기존 개념을 참고한 방향 제시이며, 실제 2차 구현 시 구체적인 라우팅 로직은 별도로 설계해야 합니다.
- 이 보고서는 코드 변경 없이 데이터 조회만 수행했으며, Supabase 조회는 읽기 전용 SELECT만 사용했습니다.
