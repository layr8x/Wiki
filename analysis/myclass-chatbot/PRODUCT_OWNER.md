## 1. 제품 비전 & 문제 정의

### 1.1 비전 (한 문장)

> **"학부모·학생이 전화·카카오로 묻던 학원 운영 질문을, 앱 안에서 30초 안에 스스로 해결하게 한다."**

마이클래스 챗봇은 *상담 채널*이 아니라 **셀프서비스 레이어**다. "사람을 빨리 연결하는 봇"이 아니라 "사람을 부를 필요가 없게 만드는 봇"을 지향한다.

### 1.2 문제 정의 (데이터 근거)

| # | 문제 | 데이터 근거 | 비즈니스 임팩트 |
|---|---|---|---|
| P1 | **상담의 96.7%가 전화** — 셀프서비스 수단이 없음 | AMS 410,104건이 전화 접수(424,200 중) | 상담원 인건비·대기시간·야간 미응대 |
| P2 | **앱에서 막히는 것 1위 = 계정·로그인·앱 (디지털 36.7%)인데 전화로는 안 물음(0.2%)** | 카카오 오픈채팅 2,639대화(1위) vs AMS 998건(0.2%) | 막힌 사용자가 *앱 밖*으로 이탈해 카카오로 감 → 앱 안에서 못 잡음 |
| P3 | **단순 조회를 사람이 처리** — 회차/강좌 조회·문자 재발송이 전화의 큰 덩어리 | AMS 상담내용 최빈어 '주차' 42,484·'회차' 20,445, 동영상보강 32,358·동보자료 31,690, '문자' 15,818 | 자동화 가능한 일을 사람이 함 (낭비) |
| P4 | **결제 재시도 마찰 + 미납 잔여** (※ "이탈 61%"는 측정 착시) | 실사용자 결제완료 ~80%(정상). 1인당 `enter_payment` 평균 3.37회. 미납 8,954건 | 이탈 손실은 과장이었으나, 재시도 마찰·미납 회수는 실재 |
| P5 | **입반·대기 수요가 전화에 갇힘** — 디지털 셀프 미충족 | AMS 입반 93,478·대기 26,724, 재수강확인 10,965·대기번호 3,170·충원 11,523 | 단순 상태조회까지 전화로 처리 |

> **착시 정정(중요)**: v1/v2에서 "결제 이탈 61% = 최대 손실"이라 한 것은 **틀렸다**. 원천 이벤트(`events_*`)를 직접 분석하니 실사용자 기준 결제완료 ~80%(정상). 외부 결제모듈(sdijeon 공통 PG) 왕복이 GA4상 "빈 구간"으로 보였던 것. → 결제 메뉴의 가치는 "이탈 막기"가 아니라 **미납 회수 + 재시도 마찰 완화 + 외부모듈 왕복 안내**(톤 = "도와주기").

### 1.3 핵심 통찰 — 전화와 디지털은 정반대다

| | AMS 전화 1위 | 디지털(오픈채팅) 1위 |
|---|---|---|
| **무엇** | 출결 30.7% | 계정·로그인·앱 36.7% |
| **왜** | 출결은 앱에서 *잘 써서* 전화로만 물음(GA4 `/classes` 216만 = 정상 작동) | 디지털은 *막혔을 때* 찾는 곳(앱 안 됨·로그인·등록·결제·환불) |

→ **챗봇은 앱 안에 산다 → 디지털 기준으로 메뉴를 배치한다.** 출결·시간표는 "도움요청"이 아니라 "**조회 기능**"으로 둔다.

## 2. 목표 & 성공지표 (KPI)

> 측정 가능 정의 + 목표치 + 산정식. **가설 기반 목표치는 [가설]로 명시**. 베이스라인이 없는 초기 출시이므로, 출시 후 2주를 베이스라인 측정 구간으로 둔다.

### 2.1 North Star Metric (단 하나의 지표)

> **자가해결율 (Self-Resolution / Deflection Rate) = 챗봇 세션 중 사람 연결(상담실·카톡 채널) 없이 종료된 비율**

- **정의**: `(챗봇 세션 수 − 사람 연결 세션 수) ÷ 챗봇 세션 수`
- **목표치(v1)**: **≥ 55%** [가설 — 커버리지 추정 50~60% 근거]
- **의미**: 셀프서비스 흡수의 단일 대리지표. 모든 메뉴·노드(막다른 길 0) 설계가 이 숫자로 수렴.

### 2.2 KPI 트리

| 영역 | 지표 | 정의(산정식) | v1 목표 | 근거 |
|---|---|---|---|---|
| **흡수(NSM)** | 자가해결율 | 사람 연결 없는 세션 ÷ 전체 세션 | **≥55%** [가설] | 커버리지 50~60% |
| 흡수 | 1차 자동응답 해결율 (Self-Serve Resolution) | "다 해결됐어요" 클릭 또는 사람 연결 없이 종료 ÷ 전체 | **≥45%** [가설] | T1+T2 케이스 비중 |
| 흡수 | 채널 전환(전화→챗봇) | 챗봇 세션 수 / (챗봇+전화 접수) 추세 | 출시 후 ↗ 추세 | 전화 96.7% 흡수가 핵심 |
| **출결·보강** | 출결·보강 조회 흡수 | 출결·보강 진입 세션 중 사람 연결 없음 ÷ 진입 | **≥50%** [가설] | 출결 30.7%(전화 1위)·보강 조회 자가완결 가능 |

### 2.3 측정 인프라 [확인필요 — 개발]

- 모든 노드에 이벤트 로깅: `chatbot_open`, `menu_select`, `node_view`, `resolved_yes`, `handoff_open`, `notif_optin`, `notif_click`, `csat`.
- 세션 정의: 챗봇 오픈 ~ 종료(또는 30분 idle).
- 상담 재질문율은 상담 시스템과 연계 필요 → v1은 **사람 연결 시 학생·지점·문의유형 첨부 여부**(전달 완전성)를 대리지표로.

## 3. 우선순위 (MoSCoW)

> Must = 6/18 핸드오프 필수 · Should = 빠른 후속 · Could = 여유 시 · Won't = 이번 범위 밖.
> 분류 기준: **디지털 채널 볼륨 × 자가해결 가능성 × 데이터 의존도(낮을수록 빠름)**.

### 3.1 메뉴 4종 (v6, `기획서_v6_요약.md §2`)

> v6 4메뉴는 전화 최다 수요(출결·보강·결제·시간표)를 겨냥한 조회 중심. v5(5메뉴)에서 입반·등록·대기 메뉴를 삭제하고 '입반 강좌 확인'을 출결·보강으로 흡수했다. 옛 8메뉴(v3)의 계정·로그인·앱 / 라이브·교재·배송 / 퇴원 / 상담·FAQ는 v6에 별도 메뉴로 없다.

## 4. MVP (v1) 범위 — v6 4메뉴

> v6 4메뉴 빌드는 **4개 메뉴 전체 + 하위 노드(막다른 길 0)**를 모두 클릭 가능하게 구현. 각 메뉴는 DB 의존이 높은 부분은 안내+상담 연결로 우아하게 격하한다. 노드별 답변 포맷은 `기획서_v6_요약.md §3`.

### 4.3 v1 자가해결 가설 (왜 이 범위로 충분한가)

v6 4메뉴는 전화 최다 수요(출결 30.7% + 결제·미납 + 회차 조회)를 직접 겨냥한다. 인앱 챗봇은 로그인 후에 사는데 디지털 최대수요(계정·로그인 36.7%)는 로그인 전에 발생해 챗봇이 못 닿으므로, 흡수 타깃을 **전화의 출결·보강·결제·시간표**로 좁혔다. DB 의존이 높은 부분(보강 정밀 조회)은 안내+상담 연결로 격하해 NSM 손실을 막고, 조회 완결형 4메뉴로 **자가해결율 55% 목표**를 겨냥한다.

## 5. 기능별 인수기준 (Acceptance Criteria) — 상위 6개

> Given-When-Then 형식. 각 시나리오는 `QUICK_MENU_SCENARIOS.md`/`CHATBOT_PLAN.md`의 플로우에 대응.

### AC-1. 📋 출결·보강 (오늘 출석 · 보강 · 입반 강좌 확인)

```
Given 사용자가 출결·보강 메뉴에 진입하면
When  [오늘 출석 확인] / 강좌 선택→[동영상 보강/타반보강/추가영상] / [입반 강좌 확인] 중 선택하면
Then  오늘 출석은 강좌별 수업시간·출결상태(출석/출석예정)를, 보강은 회차별 상태를 조회해 카드로 보여준다
And   동영상 보강은 마이클래스(VOD)/연구실 동영상/시청시간 포맷으로, 강좌 선택은 입반 완료 강좌만 노출한다
And   데이터 없음(타반보강 없음 등)은 상담 연결로 잇고, 각 화면 하단에 [이전][처음으로]가 항상 존재한다
```
- **수용 조건**: 입반 중인 강좌가 없으면 `현재 입반 중인 강좌가 없어요.` 안내. 막다른 길이 0개.

### AC-2. 💳 납부·결제 (납부 현황 + 납부하기 화면 + 결제 내역)

```
Given 사용자가 납부·결제 메뉴에서 [납부 현황]을 선택하면
When  수납 DB를 조회하면
Then  PayCard에 `[납부필요]` + `[납부대기 or 가상계좌 입금 대기]` 2섹션(수강료·교재비·합계·납부기한)으로 표시된다
And   주행동 [납부하기]는 마이클래스 "납부하기" 화면(외부 결제창 왕복)으로 이동하고, 가상계좌는 번호 전체노출+복사된다
And   [결제 내역]은 최근 3개월(결제일·강좌명 외 N건·금액·수단·상태[결제완료/부분환불])로, 전체완납이면 `모든 수강료가 납부 완료됐어요.`
```
- **수용 조건**: 결제 톤은 "이탈 막기"가 아니라 "도와주기". 판단·거래는 상담 연결.

### AC-3. 📅 수업·시간표 (조회형 자가완결)

```
Given 사용자가 수업·시간표 메뉴에서 [내 시간표] / [강좌별 전체 회차 일정] / [종강일 확인]을 선택하면
When  시간표/학사 API를 조회하면
Then  내 시간표는 이번 주 요일별 블록·강의실을(다음 주 보기 가능), 전체 회차 일정은 강좌 선택 후 회차별 일정 + `전체 N회 중 M회차 진행 중`을 표시한다
And   종강일 확인은 강좌별 종강일(YYYY-MM-DD)을 보여주고 휴강·일정 변경은 상담 연결로 잇는다
And   조회 키는 강좌 단위이며, 각 화면 하단에 [이전][처음으로]가 존재한다
```
- **수용 조건**: 시간표·회차·종강일 조회가 사람 연결 없이 완결된다.

### AC-4. 사람 연결 — 상담 연결(전화)

```
Given 자가해결이 안 되거나 판단·거래가 필요하면
When  상담 연결이 필요하면
Then  [상담 연결](전화)로 지점별 전화번호를 노출한다 ([상담 등록] 버튼은 제거됨)
And   카드에 학생·지점·문의유형이 자동 표기되어 재질문을 줄인다
And   늦은 시간(22–08시)이면 "문자 남기면 운영 시작 시 먼저 연락"+셀프 안내로 분기한다
```
- **수용 조건**: 막다른 길 없음. 컴플레인은 추측 응답 없이 즉시 상담 연결.

### AC-5. 진입 & 첫 인사 (게이트 없음)

```
Given 사용자가 로그인된 마이클래스 앱에서 챗봇을 열면
When  챗봇이 열리면
Then  별도 본인확인 게이트 없이 "안녕하세요, 김시대님. 대치 캠퍼스 기준으로 안내해 드릴게요."로 인사하고
And   4메뉴 타일(출결·보강 / 납부·결제 / 수업·시간표 / 전반)을 노출한다
And   헤더 우상단은 닫기 X 하나만 두고(홈 버튼 없음), 2Depth 이상 화면엔 [이전][처음으로]를 둘 다 노출한다
```
- **수용 조건**: 로그인 세션의 학생·지점이 인사·카드에 반영된다. 본인 데이터만 조회.

### AC-6. 능동 알림 N2 (미납) — MVP 알림

```
Given 사용자가 납부 알림에 옵트인했고, 미납이 발생하면
When  기한 D-3 / D-1 / D-day 시점이 되면
Then  "7월 수강료 미납, 기한 D-2" 메시지와 [지금 결제]·[문자 다시] 액션을 푸시한다
And   1인/일 3건 한도·야간(21–08) 금지·번호 마스킹·중복발송 차단 규칙을 지킨다
And   알림 클릭 → 7일 내 결제완료를 미납 회수 KPI로 집계한다
```
- **수용 조건**: 옵트인 없으면 미발송. N4(대기충원)만 야간 예외 허용.

## 6. 범위 밖(Out of Scope) · 가정(Assumptions) · 의존 리스크(Dependencies & Risks)

### 6.1 명시적 범위 밖 (Out of Scope)

| 항목 | 사유 / 대안 |
|---|---|
| 자유 텍스트 LLM 대화(오픈엔디드 챗) | v1은 버튼/카드 기반 결정형 플로우. 인텐트 분류는 규칙기반 v1 |
| 환불 예상액 자동 계산 | 교육청 규정 미확정 → 표시치만, 정확 금액은 상담 확정 |

| 다국어 | 한국어만 |
| 데스크톱 전용 레이아웃 | 모바일 95.8% → 모바일 우선(바텀시트). 태블릿·데스크탑은 도킹 패널(392×700) |

### 6.2 가정 (Assumptions)

1. 챗봇은 로그인된 앱 세션 안에서 열려, 학생·지점을 세션에서 받는다(별도 본인확인 게이트 없음).
2. 결제는 외부 PG "납부하기" 화면으로 이동 후 콜백으로 확인된다.
3. 출결·보강·납부·시간표 데이터는 조회 API로 실시간 접근 가능하다.
4. 사람 연결은 상담 연결(전화, 지점별 번호) 하나로 단순화한다.
5. 디지털 채널 분포(오픈채팅 7,213 분류)가 챗봇 실제 수요를 대표한다.
6. v1 자가해결율 베이스라인은 출시 후 2주간 측정으로 확정한다.

### 6.3 의존 리스크 (개발팀 [확인필요] — 우선순위순)

| # | 의존 항목 | 영향 메뉴 | 리스크 | 미충족 시 폴백 |
|---|---|---|---|---|
| 1 | 수납 DB(납부 현황·결제 내역·가상계좌) | 납부·결제 (Must) | **高** — 없으면 납부·결제 핵심 깨짐 | 안내+상담 연결로 격하 |
| 2 | 강좌·회차 단위 보강/시청권 API | 출결·보강 (Must) | **高** | 보강 정밀 조회 v1.x 연기, 상담 연결로 |
| 3 | 로그인 세션 학생·지점 전달 | 전체 개인화 | **高** | 비개인화 안내+상담 연결 |
| 4 | 시간표·회차·종강일 API | 수업·시간표 (Should) | 中 | 조회 축소·상담 연결 |
| 5 | 결제 외부모듈 상태 콜백·미반영 조회 | 납부·결제 | 中 | "1–2분 지연" 안내+상담 연결 |
| 6 | 능동알림 실시간 이벤트 소스·푸시 인프라·미성년 동의 | N2/N4/N1 | **高(법적)** | 알림 전체 v1.x 연기 |
| 7 | 전반 가능 강좌 조회(지점단과별) | 전반 (Could) | 中 | 안내+상담 연결 |
| 8 | 상담 연결 지점별 전화번호 확정 | 공통(상담 연결) | 低 | 대표번호로 |
| 9 | KPI 이벤트 로깅 스키마 | 측정 전체 | 中 | NSM 측정 불가 → 출시 후 보강 |
| 10 | 진입 맥락 트리거(`page_path` 이벤트) | 진입 배너 | 低 | 정적 진입(배너 없음) |

> **리스크 대응 원칙**: DB 의존이 높은 기능은 "조회 → 안내+상담 연결"로 우아하게 격하(graceful degradation)할 수 있도록 설계한다. v1 상담 연결(전화)은 어떤 경우에도 작동하는 최종 안전망이다.
