# 상담 데이터 이상탐지·알림 설계

> **3줄 요약**
> 1. 상담 데이터로 **운영 사고를 조기에 잡는 자동 알림** 2종을 설계하고, 실제로 SQL을 돌려 작동을 확인했습니다 — (A) 특정 문의 **급증**(시스템 장애 신호), (B) 상담 **수집 중단**(데이터가 멈춤).
> 2. **★ 지금 실제로 사고가 진행 중입니다** — 3개 채널 모두 **2026-06-26부터 신규 수집이 멈췄습니다**(인증 쿠키 만료, `poll 401 Unauthorized`). "살아있는 척"하는 heartbeat 때문에 눈에 안 띄던 사고를, 이 알림이 즉시 잡아냅니다.
> 3. 알림은 Slack/이메일로 보내되, **"심장은 뛰는데 데이터가 0"** 같은 함정까지 잡도록 설계했습니다(heartbeat만 보면 못 잡음).

## 0. 한눈에 (비개발자용)

상담 데이터는 두 가지 방식으로 운영 문제를 **먼저** 알려줍니다.

1. **갑자기 특정 문의가 폭증** = 어딘가 고장났다는 신호입니다. 예를 들어 "결제 오류" 문의가 평소의 3배가 되면, 결제 시스템에 장애가 났을 가능성이 큽니다. 학부모 불만이 쌓이기 **전에** 알아챌 수 있습니다.
2. **상담이 갑자기 안 들어옴** = 수집 장치가 멈췄다는 신호입니다. 학부모가 문의를 안 한 게 아니라, **우리가 못 받고 있는 것**일 수 있습니다.

지금 바로 **2번 사고가 진행 중**입니다. 수집기가 카카오에 로그인하는 열쇠(쿠키)가 만료돼, 6월 26일부터 새 상담이 한 건도 안 들어오고 있습니다. 그런데 수집기의 "심장박동(heartbeat)"은 계속 뛰고 있어서, 겉보기엔 멀쩡해 보입니다. 이 문서의 알림은 바로 이런 **"멀쩡한 척하는 고장"** 을 잡습니다.

## 1. 알림 (A) — 카테고리 급증 탐지 (시스템 장애 조기 신호)

### 1-1. 아이디어
"오늘 어떤 카테고리의 문의 수가 **직전 7일 평균의 2배 이상**이면 경보." 결제오류·계정 문의가 갑자기 튀면 = 시스템 장애 가능성.

### 1-2. 작동 SQL (실행 확인 완료)

```sql
-- 일자별 카테고리 카운트 vs 직전 7일 평균 대비 급증 탐지
WITH daily AS (
  SELECT date_trunc('day', c.last_log_send_at)::date AS d, c.category, count(*) AS cnt
  FROM kakao_partner_chats c
  WHERE c.category IS NOT NULL
  GROUP BY 1, 2
),
roll AS (
  SELECT d, category, cnt,
    avg(cnt) OVER (PARTITION BY category ORDER BY d
                   ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING) AS baseline_7d
  FROM daily
)
SELECT d, category, cnt, round(baseline_7d, 1) AS baseline_7d,
       round(cnt / nullif(baseline_7d, 0), 2) AS ratio
FROM roll
WHERE baseline_7d IS NOT NULL
  AND cnt >= 5                    -- 표본 너무 적은 날 제외(노이즈 방지)
  AND cnt > baseline_7d * 2.0     -- 임계: 직전 평균의 2배 초과
ORDER BY d DESC, ratio DESC;
```

### 1-3. 실행 결과 (검증 — 최근 사례)

| 날짜 | 카테고리 | 당일 | 직전7일평균 | 배율 |
|---|---|---:|---:|---:|
| 2026-05-04 | 기타 | 12 | 1.3 | **×9.0** |
| 2026-05-11 | 계정·로그인·앱 | 16 | 3.7 | **×4.3** |
| 2026-05-26 | 기타 | 20 | 7.0 | ×2.9 |
| 2026-05-19 | 대기 | 7 | 1.1 | ×6.1 |
| 2026-05-20 | 미납·결제 | 7 | 2.1 | ×3.3 |

→ **05-11 계정·로그인 ×4.3 급증** 같은 신호를 자동으로 잡아냅니다. 이런 날 = 앱/로그인 장애를 의심할 시점.

### 1-4. 임계 튜닝
- 시작값: **배율 2.0 + 당일 ≥ 5건.** 너무 자주 울리면 2.5~3.0으로 상향, 놓치면 1.8로 하향.
- 입반 시즌(1~2월)은 전체 문의가 평시의 몇 배 → **계절성 보정**(요일·시즌 baseline 분리) 권장.

## 2. 알림 (B) — 수집 중단 감지 (★ 현재 발생 중인 사고)

### 2-1. 왜 두 신호를 같이 봐야 하나 (핵심 함정)

| 신호 | 지금 상태 | 단독으로 보면? |
|---|---|---|
| heartbeat(심장박동) | 살아있음 (0.9분 전) | ✗ "정상"으로 오판 |
| last_error | `poll 401 Unauthorized` | ✓ 사고 감지 |
| 신규 메시지 | **0건 / 95~187시간째** | ✓ 사고 감지 |

→ **heartbeat만 보면 "정상"으로 보입니다.** 그래서 `last_error` + `신규 메시지 0` 을 **함께** 봐야 진짜 사고를 잡습니다.

### 2-2. 작동 SQL — 통합 헬스체크 (실행 확인 완료)

```sql
-- 채널별 수집 건강 상태: heartbeat가 살아있어도 메시지 0이면 잡는다
SELECT
  CASE s.profile_id WHEN '_xfxilXn' THEN '시대인재C'
                    WHEN '_TkpPG'   THEN '라이브'
                    WHEN '_VGAQn'   THEN '마이클래스' ELSE s.profile_id END AS channel,
  round(EXTRACT(EPOCH FROM (now() - s.last_heartbeat_at))/60.0, 1) AS hb_age_min,
  (s.last_error IS NOT NULL AND s.last_error_at > now() - interval '15 min') AS err_recent,
  (SELECT round(EXTRACT(EPOCH FROM (now() - max(m.sent_at)))/3600.0, 1)
     FROM kakao_partner_messages m WHERE m.profile_id = s.profile_id) AS hrs_since_msg,
  CASE
    WHEN s.last_error IS NOT NULL AND s.last_error_at > now() - interval '15 min'
         THEN '🔴 수집중단(인증오류)'
    WHEN (SELECT max(m.sent_at) FROM kakao_partner_messages m
            WHERE m.profile_id = s.profile_id) < now() - interval '6 hours'
         THEN '🟠 신규메시지 끊김'
    WHEN s.last_heartbeat_at < now() - interval '15 min'
         THEN '🟠 heartbeat 끊김'
    ELSE '🟢 정상'
  END AS health
FROM kakao_partner_stream_state s
ORDER BY s.profile_id;
```

### 2-3. 실행 결과 (검증 — 2026-06-30 라이브)

| 채널 | heartbeat 경과 | 최근 에러? | 마지막 메시지 경과 | 판정 |
|---|---:|:---:|---:|---|
| 시대인재C | 0.9분 | 예 | **96.1시간** | 🔴 수집중단(인증오류) |
| 라이브 | 0.9분 | 예 | **187.0시간** | 🔴 수집중단(인증오류) |
| 마이클래스 | 0.9분 | 예 | **95.0시간** | 🔴 수집중단(인증오류) |

- **3채널 전부 🔴.** heartbeat는 1분 내로 멀쩡한데(심장은 뜀), 신규 메시지는 **4~8일째 0건**.
- `last_error` = `poll 401 ... {"message":"Unauthorized"}` → **인증 쿠키 만료**. 마지막 정상 수집: 마이클래스 06-26 04:17, 시대인재C 06-26 03:11, 라이브 06-22 08:20.

### 2-4. 더 단순한 보조 SQL (둘 중 하나만 써도 잡힘)

```sql
-- (B-1) 에러 기반: 최근 30분 내 에러가 있으면 ALERT
SELECT profile_id, last_error, last_error_at,
  CASE WHEN last_error IS NOT NULL AND last_error_at > now() - interval '30 min'
       THEN 'ALERT' ELSE 'OK' END AS status
FROM kakao_partner_stream_state;

-- (B-2) 메시지 공백 기반: 최근 6시간 신규 메시지 0이면 ALERT
SELECT profile_id, max(sent_at) AS last_msg_at,
  CASE WHEN count(*) FILTER (WHERE sent_at > now() - interval '6 hours') = 0
       THEN 'ALERT: 신규 수집 없음' ELSE 'OK' END AS status
FROM kakao_partner_messages
GROUP BY profile_id;
```

> **당장 할 일(운영팀):** 카카오 비즈채팅 로그인 쿠키를 **재발급**해 수집기에 다시 넣어야 합니다. 그래야 06-26 이후 멈춘 신규 상담 수집이 복구됩니다.

## 4. 알림 채널 연동 개념도 (Slack / 이메일)

```
[스케줄러: cron 또는 Supabase Edge Function]
        │  (5~10분마다 / 1시간마다)
        ▼
[탐지 SQL 실행]  ─ (A)급증  ─ (B)수집헬스
        │
        ▼
[판정] 🔴/🟠 행이 있나?
        │ 있음                       │ 없음
        ▼                            ▼
[알림 발송]                         (조용)
   ├─ Slack: webhook 으로 채널에 메시지
   │    "🔴 [수집중단] 라이브·마이클래스·C — 인증오류 401, 신규 0건(4~8일)"
   └─ 이메일: 운영 담당자에게 요약 + 조치 링크
        │
        ▼
[중복 억제] 같은 사고는 1회만(쿨다운), 해소되면 '복구' 알림
```

### 연동 방식 (택1)
- **간편**: Supabase **Edge Function**(스케줄) 안에서 위 SQL 실행 → 결과가 🔴면 **Slack Incoming Webhook**으로 POST. 코드 짧고 외부 서버 불필요.
- **확장**: 별도 워커(GitHub Actions cron 등)가 SQL 실행 → Slack + 이메일(예: Resend/SES) 동시 발송, 사고 이력 테이블에 기록.

### 알림 문구 예시 (Slack)
```
🔴 카카오 상담 수집 중단
• 채널: 라이브·마이클래스·시대인재C (3/3)
• 원인: poll 401 Unauthorized (인증 쿠키 만료)
• 마지막 수집: 06-26 04:17 (마이클래스) ~ 06-22 08:20 (라이브)
• 조치: 카카오 비즈채팅 쿠키 재발급 → 수집기 재기동
```
