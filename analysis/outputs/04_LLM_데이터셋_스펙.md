# 상담대화 → LLM 학습·평가 데이터셋 자산화 스펙

> **3줄 요약**
> 1. 이미 쌓인 카카오 상담 **8.6만 메시지**에서 "학부모 질문 ↔ 상담원 답변" 쌍만 골라내면, 돈 들이지 않고 **약 1.9만 건의 실전 Q&A 데이터셋**을 만들 수 있습니다 (실측: 인접 질문-답변 쌍 **19,308건**).
> 2. 이 데이터셋의 쓰임새는 3가지 - ① 챗봇 답변이 맞는지 채점하는 **평가셋**, ② 문의 자동분류 모델 **학습 재료**, ③ 사람처럼 답하는 2차 챗봇의 **예시(few-shot)**.
> 3. 단, 상담 원문에는 개인정보가 섞여 있으므로 **마스킹·품질정제 단계를 반드시 통과**시킨 뒤에만 자산으로 씁니다. 이 문서는 그 추출 방법·스키마·규모를 실측으로 정리한 설계도입니다.

---

## 0. 한눈에 (비개발자용)

지금 우리 보관함(데이터베이스)에는 학부모가 카톡으로 물어본 내용과 상담원이 답한 내용이 **시간순으로 그대로** 쌓여 있습니다. 마치 통화 녹취록이 한 줄 한 줄 저장된 것과 같습니다.

이걸 그냥 두면 "지난 기록"일 뿐이지만, **"질문 한 줄 + 그 바로 다음 답변 한 줄"을 짝지어 빼내면** 그 자체가 "이런 질문엔 이렇게 답한다"는 **정답지 묶음**이 됩니다. 이 정답지는:

- 새로 만든 챗봇이 **상담원만큼 잘 답하는지 채점**하는 시험지로 쓰고,
- 문의를 자동으로 분류하는 기계(모델)를 **가르치는 교과서**로 쓰고,
- AI에게 "이렇게 답해줘" 하고 **본보기로 몇 개 보여주는** 용도로 씁니다.

즉, **이미 가진 데이터를 한 푼도 더 안 들이고 학습 자산으로 바꾸는 것**이 이 문서의 목표입니다.

## 1. 무엇을 만드나 - 산출물 정의

| 산출물 | 한 줄 정의 | 형태 |
|---|---|---|
| **Q-A 코퍼스** | "학부모 질문 → 상담원 답변" 1:1 쌍 모음 | JSONL(한 줄=한 쌍) |
| **분류 라벨셋** | 각 쌍에 붙은 카테고리(예: 환불, 계정·로그인) | 위 코퍼스의 컬럼 |
| **평가 골든셋** | 사람이 한 번 더 검수한 고신뢰 부분집합 | 위에서 추린 소수 정예 |

핵심은 **"인접 쌍(adjacent pair)"** - 같은 대화방(`chat_id`) 안에서, 학부모(`user`)가 보낸 메시지 **바로 다음에** 상담원(`manager`)이 보낸 메시지를 하나의 Q-A로 묶습니다. 사람이 실제로 주고받은 순서를 그대로 쓰므로 "지어낸 답"이 아니라 **실전 정답**입니다.

## 2. 데이터 추출 방법

### 2-1. 원천 테이블 (Supabase, project `bnszzjaupayakkahmwsu`)

| 테이블 | 역할 | 쓰는 컬럼 |
|---|---|---|
| `kakao_partner_messages` | 메시지 한 줄씩 | `chat_id`, `sender_type`, `message`, `message_type`, `sent_at`, `profile_id` |
| `kakao_partner_chats` | 대화방 요약·분류 | `chat_id`, `category`, `category_confidence`, `profile_id` |

- `sender_type` = `user`(학부모) / `manager`(상담원) / `system`(자동 알림).
- `message_type = '1'` = 일반 텍스트. 사진·파일·시스템메시지(`71` 등)는 제외.
- `profile_id` = 채널 구분: `_xfxilXn`=시대인재C, `_TkpPG`=라이브, `_VGAQn`=마이클래스.

### 2-2. 추출 로직 (말로 풀면)

1. 한 대화방 안의 메시지를 **시간순으로 줄 세운다.**
2. 각 메시지의 "바로 다음 줄 발신자"를 본다(`LEAD`).
3. **현재 줄이 학부모(user)이고 + 다음 줄이 상담원(manager)** 이면 → 그 둘을 Q-A로 묶는다.
4. 질문·답변 둘 다 글자가 2자 이상인 것만 남긴다(빈말 제거).

### 2-3. 추출 SQL (검증 완료 - 실제 실행함)

```sql
WITH ordered AS (
  SELECT m.chat_id, m.profile_id, m.sender_type, m.message, m.sent_at,
         lead(m.sender_type) OVER (PARTITION BY m.chat_id ORDER BY m.sent_at) AS next_sender,
         lead(m.message)     OVER (PARTITION BY m.chat_id ORDER BY m.sent_at) AS next_msg,
         lead(m.sent_at)     OVER (PARTITION BY m.chat_id ORDER BY m.sent_at) AS next_at
  FROM kakao_partner_messages m
  WHERE m.message_type = '1'              -- 텍스트만
    AND m.sender_type IN ('user','manager')
    AND m.message IS NOT NULL AND length(trim(m.message)) > 0
)
SELECT o.chat_id,
       o.profile_id                       AS channel_id,
       o.message                          AS question,     -- 학부모 질문
       o.next_msg                         AS answer,       -- 상담원 답변
       o.sent_at                          AS asked_at,
       c.category                         AS category,     -- 분류 라벨
       c.category_confidence              AS category_conf
FROM ordered o
JOIN kakao_partner_chats c ON c.chat_id = o.chat_id
WHERE o.sender_type = 'user' AND o.next_sender = 'manager'
  AND length(trim(o.message))  >= 2
  AND length(trim(o.next_msg)) >= 2;
```

> 한 학부모가 연달아 여러 줄 보낸 뒤 상담원이 답하는 경우, 위 로직은 "상담원 답 직전 마지막 질문 줄"만 짝지습니다. 더 자연스러운 학습을 원하면 부록 A의 "발신자 연속 합치기(turn merge)" 변형을 씁니다.

## 3. 스키마 (데이터셋 한 줄의 모양)

JSONL 한 줄 = Q-A 한 쌍. 예시(값은 가상·마스킹):

```json
{
  "id": "qa_000001",
  "chat_id": "c_******",
  "channel": "마이클래스",
  "question": "앱 로그인이 자꾸 [전화번호] 오류가 떠요",
  "answer": "안녕하세요 학부모님, 비밀번호 재설정 후 ...",
  "category": "계정·로그인·앱",
  "category_conf": 0.70,
  "asked_at": "2026-06-20T09:11:00+09:00",
  "split": "train",
  "pii_masked": true,
  "quality": "ok"
}
```

| 필드 | 뜻 | 출처 |
|---|---|---|
| `question` | 학부모 질문 원문(마스킹 후) | `messages.message` (user) |
| `answer` | 상담원 답변 원문(마스킹 후) | 인접 다음 `manager` 메시지 |
| `category` | 13종 카테고리 | `chats.category` |
| `category_conf` | 분류 신뢰도(0.30 또는 0.70) | `chats.category_confidence` |
| `channel` | 시대인재C / 라이브 / 마이클래스 | `profile_id` 매핑 |
| `split` | train / valid / test | 정제 단계에서 부여 |
| `pii_masked` | 개인정보 마스킹 통과 여부 | 정제 단계 |
| `quality` | ok / drop / review | 정제 단계 |

## 4. 활용 3가지

### ① 챗봇 답변 품질 **평가셋**
- "이 질문에 상담원은 이렇게 답했다"가 정답. 챗봇 답을 같은 질문에 넣고, **상담원 답과 얼마나 가까운지** 채점합니다.
- 사람 채점(소수 골든셋) + 자동 채점(LLM-as-judge) 병행. 카테고리별 정확도를 따로 봐서 약점 영역을 찾습니다.

### ② 문의 자동분류 모델 **학습 재료**
- `question` → `category`가 그대로 (입력, 정답) 학습쌍입니다.
- **단, '기타'(신뢰도 0.30)는 학습에서 빼거나 따로 다룹니다** - 잘못 붙은 라벨이 많아 모델을 망칩니다(→ `05_상담분류_고도화.md`와 연결).

### ③ 2차 LLM 자연어 응대 **few-shot 예시**
- 챗봇이 새 질문을 받으면, **비슷한 과거 Q-A 몇 개를 본보기로 함께 보여주고** "이 톤·이 정책으로 답해" 시킵니다.
- 상담원의 실제 화법·정책 표현이 그대로 들어가므로 **우리 학원 말투**가 재현됩니다.

## 5. PII·품질 정제 단계 (자산화 전 필수 관문)

> 상담 원문은 대외비이자 개인정보를 포함합니다. 아래 5단계를 통과한 데이터만 자산으로 씁니다.

| 단계 | 하는 일 | 통과 기준 |
|---|---|---|
| **1. 1차 마스킹 확인** | 수집 시 마스킹된 전화·이름이 남았는지 재점검 | 패턴 검사 0건 |
| **2. 2차 PII 마스킹** | 남은 전화/계좌/주소/실명을 `[전화]`·`[계좌]` 등으로 치환 | 정규식 + 사전 |
| **3. 노이즈 제거** | "넵/감사/ㅎㅎ" 등 내용 없는 답, 빈 답, 자동응답 제거 | 길이·키워드 필터 |
| **4. 중복 제거** | 같은 질문-답변 반복(템플릿 답변) 압축 | 정규화 후 dedup |
| **5. 분할·라벨검수** | train/valid/test 나누고 골든셋만 사람 검수 | test는 100% 검수 |

마스킹 자동검사 예시:

```sql
-- 데이터셋에 전화/계좌 흔적이 남았는지 사전 점검(0이어야 통과)
SELECT count(*) AS suspect
FROM kakao_partner_messages
WHERE message_type='1' AND sender_type IN ('user','manager')
  AND message ~ '01[016-9][0-9]{7,8}|[0-9]{2,3}-[0-9]{3,4}-[0-9]{4}';
```

## 부록 A. 기술 부록

### A-1. 발신자 연속 합치기(turn merge) 변형
학부모가 3줄 연달아 보낸 뒤 상담원이 답하면, 위 기본 로직은 마지막 1줄만 질문으로 씁니다. 전체 맥락을 살리려면 **같은 발신자의 연속 메시지를 하나의 turn으로 합친 뒤** 인접 쌍을 만듭니다(`gaps & islands` 패턴: `row_number()` 차이로 그룹핑 → `string_agg`).

### A-2. 분할 비율 권장
- train 80% / valid 10% / test 10%. **test는 시간 기준(최근 N주)으로 잘라** 미래 일반화 성능을 봅니다(랜덤 분할은 데이터 누수 위험).

### A-3. 라벨 신뢰도 주의
- 현재 `category_confidence`는 **0.70(규칙 매칭) 또는 0.30(미매칭='기타')** 두 값뿐 (실측). 0.30은 사실상 "분류 실패" 신호 → 학습 제외 권장.

### A-4. 갱신 주의
- 상담 데이터는 매일 갱신됩니다. 데이터셋 버전을 끊을 때마다 추출 쿼리를 **재실행하고 추출 시각·건수를 버전 메타에 기록**합니다.
